# 实际游玩的卡顿记录

正式游戏启动即记录，不必按键开始。不改战斗、光照、地图、特效，不录屏。

- F3：隐藏／迷你／详细显示，隐藏仍记录。
- F4：保存当前记录并查看报告。玩完建议按一次，再正常退出。
- “保存本局并开始新记录”：保留前一份，创建新目录，不清除旧记录。

每次启动创建独立目录：

`%APPDATA%/Godot/app_userdata/Five Minutes More改版/performance_runs/日期时间_进程号_启动时刻/`

目录包含：

- `metadata.json`：版本、列定义、图形设置、统计口径。
- `frames.csv`：逐采样间隔的帧耗时、脚本与物理回调区间、物理补步、上次绘制区间、主视口绘制量、资源计数、楼层／房间／种子／位置、系统内存，以及烟雾、角色桥接、遮挡、血迹、敌人、门碎片分阶段耗时。版本4共164列，以 metadata 的列定义为准；旧记录不改写。
- `events.jsonl`：消防器破裂／碰撞／停下、发射弹丸、近战、受伤、击杀、门窗／家具破坏、爆炸、换房、切层、图形设置变动等时间线。高频事件在一个采样间隔内聚合，保留总数、首末时刻与最多四个示例。
- `summary.json`：F4／正常退出时保存的整局统计及最严重的40个游玩帧。
- `report.txt`：可阅读的报告。

`user://perf_run_report.txt` 仍是 F4 导出的便捷文本副本，独立记录不会因下一次启动而覆盖。

## 记录与分析边界

1. “全部游玩”包含首次和加载后2.5秒的预热段；另列预热和稳态，不把首用卡顿藏掉。
2. 加载、暂停、失焦、报告界面单独标注；单帧超过1秒本身不是加载证据。跨出这些状态的一个采样间隔也单独标注，避免把切回游戏的等待归入游玩。
3. 直方图覆盖整次运行。百分位向上取整到0.1ms；最大值、总时长、阈值计数保留原始精度。>20ms 与 >33.3ms 统计为帧数，不是假装每一帧都是独立卡顿事件。
4. CPU脚本／物理为场景回调的首末区间，不是原生服务器完整耗时。`draw_span_ms` 是上次 `frame_pre_draw` 到 `frame_post_draw`，不是纯GPU耗时。用 `draw_process_frame` 关联对应轮次。
5. 视口CPU/GPU和全局绘制计数来自先前完成的渲染，可能滞后一帧或更多。根视口与世界视口时间不相加；无计时支持记为 -1。Compatibility 的管线计数为0不能排除驱动编译。
6. 分组数量每0.25秒更新，`context_age_ms` 表示新旧程度；烟源／覆盖格／候选卡片每帧读取，同时另记已提交实例数。`smoke_physics` 包含其内部阶段，`smoke_coverage` 也包含内部视线更新，不重复相加。
7. 记录器主线程耗时另列，并不包含后台写盘线程CPU占用。日志由一个后台线程分批格式化与保存，不每帧主线程写盘，不扫描整棵节点树。
8. 写盘队列至多8个普通批次；落盘来不及则记录丢失量，不阻塞游玩。逐帧／事件文件各限128MB，达到上限或写盘失败会在写盘状态中明确体现，整局统计仍继续。不会自动删除既有记录。
9. 强制结束进程可能丢失末尾记录，也可能来不及生成总结；已写的帧和事件仍可分析，因此玩完按F4最稳妥。
10. 事件与峰值同时出现只是线索，不自动认定根因。没有GPU原生调用栈，不能据此声称证明某次驱动编译／资源分配是卡顿原因。
11. 版本2单列“存活游玩／存活稳态／死亡停留”。死亡事件所在采样帧保留；后续死亡停留不混入存活指标；复活或新玩家对象会重新计入。旧的“全部游玩”与最慢40帧仍完整保留，分析时不能拿含死亡停留的中位数当战斗成绩。
12. `system_free_physical_bytes` 才是可用物理内存；`system_commit_limit_bytes` 是 Windows 提交上限，不能当作空闲内存；`system_physical_total_bytes` 是系统可用物理总量。旧版 `system_available_bytes` 不能与新版空闲物理内存混用。
13. 灯光选择、预热开始／结束、血迹捕获与尸体流血、碎片材质克隆记录为有界事件；只传普通数据，不持有游戏对象。视口原生完成帧编号当前接口不可得，元数据明确标为不支持，不按固定延迟强行匹配CPU/GPU采样。
14. `smoke_fusion_snapshot` 是物理步保留融合输入的成本；`smoke_fusion_calculate` 是延后执行的重计算。后者可能落在绘制前，已包含在 `smoke_upload` 内；不能与上传、物理父区间重复相加。细分数据用于定位，不能全部相加当作整帧CPU时间。
15. 版本3将血液初始化、模拟、落地/合并、CPU提交分为 `process/physics` 两类，并分别记录 inclusive 与 self 墙钟。self 排除已打点的嵌套子区间；同类递归只记录最外层inclusive，self则保留各层独占区间。所有数值是CPU墙钟，既非原生CPU指令耗时也非GPU时间。未打点代码和等待仍可能包含在self内。
16. `scope_overhead` 只记录部分标记维护成本，不代表诊断总开销；主管构造测试中的2000次scope对照增量约6ms，不能将其当作每帧成本。`fracture_outline` 包含在 `fracture_nodes` 内，不相加。
17. `death_save_io / death_audio_ctrl / death_crt_init / death_actor_cleanup` 记录死亡适配器的同步区间，不声称覆盖所有死亡信号监听者。保存仍为原同步逻辑，未改成延后一帧或异步写盘。
18. `script_phase_trace` 在存活游玩慢帧保存有界历史：192个脚本可见边界、64个已知项目调用；普通慢帧最多200次/间隔50ms，严重帧另有64次预算/间隔5ms。summary另列预算是否用尽。加载、失焦、死亡停留不消耗此预算。CSV仍逐帧记录，不因trace限额丢掉整局分布。
19. 时间轴保留单调微秒时间、process编号、physics编号；只标记节点回调与视口更新边界，不覆盖完整原生物理步进。已知调用如血液 `mark_visual_dirty` 或 `sync_from_effect` 仅表示发生了项目方法调用，不是“已实际绘制”的名单；资源数量也不是全部资源加载/上传事件。没有全树扫描、逐帧网格哈希、原生首见列表或GPU调用栈。

20. 版本4新增 `blood_merge_prepare / frontier / fill / commit` 与 `blood_deposit_raster`。前四项包含在落地/合并父区间内，末项包含在初始化或模拟父区间内，不能重复相加。`fill`包含下一次合并邻接缓存的维护，`prepare`仍会重新读取当前血迹、变换和墙体条件；缓存只复用经完整有序像素前缀验证的邻接计数，不复用墙体/地板允许性结果。CPU提交计时和异步GPU计时仍保持区分。

自动化 `--script` 测试默认不启动记录，避免生成海量测试日志。需要检查正式记录行为时可显式调用 `start_recording()` 或加用户参数 `--perf-record`；测试必须使用隔离的用户数据目录。
