# 第一章门口与返回机库卡顿修复（2026-11-17）

已在工程源码启用修复，正常第一章试玩入口和正式 Main 的原有加载流程均接入。既有试玩入口重启后生效，本轮未导出 EXE、提交、重置或清理共享工作树。

## 原因与直接证据

原来的“每帧做一步”仍然把昂贵函数整个放进同一帧。走进 1-1 上方房间时，实际同时开始创建下一个西翼分区；返回机库与走向 1-3 又重复生成同一批材质和读取机甲模型。因此触发点看似是当前房间，重工作却来自后面的分区。

- `prepare_atrium_finishes` 每个分区重复生成约 290–300ms 的程序纹理；`prepare_atrium_weathering` 约 240ms。
- 返回机库的 `_build_endfield_signage` 再生成同一个目录牌图像，约 540ms。
- `ensure_chase_crawler` 在旧机库释放后重新读取 H06 PackedScene，约 560ms。Godot 默认资源缓存不会替代活跃引用的生命周期保留。
- 一些“单步”包含整组家具、装置或叉车；进 1-2 的第一帧还会集中创建实际敌人的显示捕获。
- 仅缓存 CPU 资源还不够。真实窗口的首次可见渲染仍触发 pipeline specialization；暂停加载期间必须实际提交渲染，并保留准备好的分区和角色捕获。关闭卸载队列的诊断仍能复现长帧，故不能把问题只归为旧场景释放。

上述函数时间来自 GDScript 调用计时；渲染首次使用由 Godot 编译计数辅助确认。`draw_span_ms` 及有延迟的视口 CPU/GPU 查询不是独立 GPU 帧时，也不据此推断精确的单帧 GPU 根因。

## 改动

1. `h06_materials.gd` 以完整参数为键缓存不可变纹理原型，每个分区仍拿到独立材质副本。目录牌和做旧纹理不再重复逐像素生成。原图像字节及材质参数逐项一致；缓存命中构建约 0.9ms。
2. `h06_gallery_art.gd` / `facility_fittings.gd` 保留世界范围的模型资源引用，H06 和现有场景资产的引用随世界释放。
3. `chapter_art.gd` 把整组道具拆为按项任务，按时间预算处理。`chapter_world.gd` 对退出分区的普通几何分叶卸载，脚本对象保持原退出生命周期。
4. 新增 `stream_render_preparation.gd`，在受遮盖且玩法冻结的加载阶段，真实渲染 WEST、返回机库及 FREIGHT。只保留当前后面的相关分区；已通过区域仍卸载，检查点不会再准备已经过去的区域。摄像机、玩家位置、生命、弹药和两条世界随机流均恢复。
5. 1-2 的实际敌人同样在加载时准备捕获；进入前隐藏、停止 AI、移出敌人组和当前逻辑房间。当前房间发现、唤醒及枪声均不能提前改变它们。进 1-2 时重新登记原对象，保留当前队伍配置、位置、武器、楼层与触发规则，不在门口重新实例化。
6. `chapter_display.gd` 复用 `scenes/ui/loading_overlay.tscn`；正式 Main 通过 `elevator_render_readiness.gd` 接入同一预备步骤。没有新增独立的提示卡或演出。

## 配对路线数据

Godot 4.7.1，Forward+ / Vulkan，RTX 5070 Ti，1280×720 原生世界视口，WASAPI、引擎启动前私有静音配置。未删除驱动缓存，数据不冒充冷驱动首次运行。对照关闭本轮三项诊断开关及材质缓存；修复组采用产品默认设置，无世界元数据覆盖。路线速度、种子 11011、两个起点和音频条件相同。

两组记录的第一章所有脚本、局部 Shader 和相关共享运行脚本 SHA256 完全一致，各自采样期间也未改变。当前共享工程的 1-2 队伍与仓库美术更新均保留，没有通过退回其他人的内容制造对照。诊断开关只供测试脚本使用。

## 加载与内存代价

本机本轮初次预备块约 **7.66s**，从 1-2 检查点进入约 **2.92s**。这是本轮新预备块的时间，不是整个游戏总启动时间，也不包括原有当前房间生成及共享武器预备流程。其他本机运行的初次预备块约6.5s，实际随驱动与并行负载改变。

首次预备后 Godot `MEMORY_STATIC` 增量约 **143.6MiB**，节点从 5861 到 11521；1-2 检查点对应增量约 54.1MiB。此计数不等于进程总内存或 GPU 显存。后续相关分区仅隐藏保留，进入后消耗，旧分区逐步释放；退出章节的世界和相关区域弱引用均已释放。
