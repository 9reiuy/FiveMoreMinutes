# PERF010｜光影与倒影重复工作：顾问统一验收

2026-11-06，Asia/Hong_Kong。**诊断已完成并独立复核。优先处理建筑补光被无关角色投影触发的缓存失效，再处理主画面与倒影的重复阴影工作。** 本轮没有制作或发布优化候选，原 C7 试玩入口、当前画面和正式游戏均保持原状。

## 已确认什么

1. **静态缓存能够工作。** 在本次办公区里，暂停玩法后保留双视口绘制，阴影提交量较低；单独小幅移动相机也未出现大幅增长。因此不能说摄像机一动，全部家具就必然重新计算或成本固定翻倍。
2. **存在不必要的补光缓存失效。** 固定场景及两个实际 Camera，只让一个既有角色投影部件运动，就会增加建筑补光的阴影绘制。补光的投影掩码已经排除了这个部件，但灯光关联掩码仍包含它。
3. **倒影会连带扩大主画面的阴影工作。** 暂停倒影更新后，减少的不仅是镜面视口的绘制，主视口的阴影提交量也明显下降。
4. **家具参与了重复绘制，但尚未测出家具自身的独立成本。** 本轮没有删除家具或敌人来制造快版本。也没有证明某一项就是全部长帧的根因。

## 同一内容的受控补证

同一小样、同一 C7、Forward+ / Vulkan、Godot 4.7.1、RTX 5070 Ti；主画面 640×360，倒影 320×180。受控段保持 104 件家具、13 个敌人节点、7 个角色接收灯。暂停玩法，只沿固定轨迹移动已有 `ActorVolumeShadow/BodyVolume/Torso` 投影几何：它在第 4 位层、仅投影，位移幅度为 ±0.2 世界单位。

| 受控条件 | 两视口渲染 CPU 合计 | 两视口 GPU 观测合计 | 主画面阴影绘制/帧 | 倒影阴影绘制/帧 |
| --- | ---: | ---: | ---: | ---: |
| 全部静止 | 1.13 ms | 5.90 ms | 441 | 173 |
| 仅一个角色投影部件运动 | 9.41 ms | 9.26 ms | 6,523 | 6,255 |
| 同一运动，保持上一张倒影纹理 | 4.28 ms | 5.89 ms | 955 | 无本帧工作 |
| 同一运动，只关闭建筑补光阴影 | 6.23 ms | 6.57 ms | 4,266 | 3,998 |
| 恢复完整双视口、同一运动 | 9.23 ms | 9.14 ms | 6,226 | 5,958 |
| 再次全部静止 | 1.11 ms | 8.51 ms | 441 | 173 |

这些是**诊断条件的成本**，不是新版本游戏帧率或可承诺的优化收益。CPU 与 GPU 不能相加当作整帧耗时；阴影绘制数不是灯数、唯一物体数或阴影贴图更新次数。

每个受控段统一使用最后 120 帧，开始于切换后第 106 帧，避开多相机状态的 60 帧迟滞；全部原始记录保留。两个实际 Camera 在受控段逐帧均只有一个姿态；投影部件的逐帧记录有 91 个不同变换。其他几何的阶段端点快照一致，但没有冒充对所有几何逐帧审计。

该轮全部失焦，各对照条件一致，不与首轮聚焦测试跨批计算提升。静态 GPU 前后存在明显波动，因此以阴影提交量和较稳定的渲染 CPU 差异判断重复工作；不将 GPU 观测差值包装成精确保证。保持旧倒影和关闭补光阴影都只是隔离手段，不能作为成品方案。

## 为什么会出现这种结果

当前补光的 `light_cull_mask=987151` 包含角色投影层 4，`shadow_caster_mask=135168` 则排除了它。引擎在能投影的几何变动时，会使关联灯的阴影失效；这条失效路径没有再按每盏灯的投影掩码筛选。本轮受控现象与这一源码机制相符。仍未取得逐灯缓存命中率，不能声称精确知道每盏灯每帧更新几次。[Godot 4.7.1 场景更新逻辑](https://github.com/godotengine/godot/blob/4.7.1-stable/servers/rendering/renderer_scene_cull.cpp#L1554)

多台相机使用同一光源时，引擎会暂时关闭更紧的阴影投影体剔除；回到单相机后有 60 个绘制帧的迟滞。主视口与倒影视口还各有阴影图集。因此，共用 World3D 不等于完全复用同一份阴影绘制。[多相机状态逻辑](https://github.com/godotengine/godot/blob/4.7.1-stable/servers/rendering/renderer_scene_cull.h#L673)、[每视口阴影图集创建](https://github.com/godotengine/godot/blob/4.7.1-stable/servers/rendering/renderer_viewport.cpp#L904)

受控补证中，停止倒影更新后，主视口阴影条目由约 6,200–6,500 降到 955，但主 CPU 本身只由约 4.5 ms 降到 4.28 ms；合计 CPU 的主要下降还来自镜面视口停止工作。**不能把绘制条目下降比例直接当成耗时下降比例。**

## 真实玩法观察及其限制

首轮保留原生 AI、物理与实际射击。完整活动段两视口渲染 CPU 合计约 17.17–17.20 ms；保持倒影时为 6.67 ms，关闭建筑补光阴影时为 10.57 ms。关闭顶灯阴影的耦合项为 9.15 ms，单独关闭角色接收灯阴影为 16.46 ms。

这些短窗口的 AI 历史不同，后段敌人数从 13 降到 12/11，独立战斗段为 10。相机节点虽然锁定，实际 Camera 仍受到原生偏移影响。因此这组数据用于成本排序，不用于计算严格的单因素收益百分比。顶灯阴影关闭还会让对应角色接收灯释放，不能与接收灯单项结果相加。

两轮记录中的全部长帧均保留。同步场景审计造成的首行边界已单列；非首行的 92.296 ms、102.069 ms 仍明确保留，尚未完成其根因归属。本轮没有重新认证手动试玩性能，也没有宣称稳定 60 FPS；用户“大部分帧不超过 80 ms”的交付口径未变。

## 下一步建议，尚未实施

| 优先级 | 建议 | 收益依据与验收重点 |
| --- | --- | --- |
| 1 | 分离光照接收与投影代理的关联，先排除补光不需要的角色投影层 | 受控关闭补光阴影减少约 1,960–2,257 条阴影提交/视口，合计 CPU 由约 9.2–9.4 ms 降至 6.23 ms。实际修正关联能收回多少仍须验证；必须保留人物亮度、建筑遮挡、断复电及动态家具效果，不能直接删补光阴影。 |
| 2 | 处理主画面和倒影对静态阴影的重复提交与缓存 | 倒影保持对照确认了直接开销和主视口的连带变化。优先保留准确的动态倒影；不能假定公开接口有直接共享阴影图集的开关。若需要引擎级改动，应先评估小探针和维护成本。 |
| 3 | 若前两项后仍不足，再考虑静态投影几何合批 | 当前大量小阴影条目提供了检查理由，但尚未测得独立收益。保持模型、碰撞和玩法，门、移动家具和破坏物必须正确退出静态批次或更新。 |

建议先制作第 1 项的最小候选，由同场景图像、开关电、角色/家具移动和成本对照决定是否保留；当前角色防自阴影修复继续保留。暂不扩大到删家具、降低倒影响应或更换渲染器。
