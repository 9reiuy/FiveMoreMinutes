# 卡通分层着色小样

2026-11-08。用户认可第二版材质，但指出没有看到独立的着色风格效果。本轮保留已认可材质，另做逐灯卡通着色层；没有推广至正式流程。

试玩入口：`tools/preview_toon_shader.cmd`。默认显示“卡通着色＋已认可材质”；T只切换卡通着色，底层已认可材质始终开启。1／2／3分别定位金属柜、塑料机壳、木桌，WASD正常走动。

## 实际变化与范围

连续受光响应改为暗／中／亮三个平台值0.15、0.55、1.0，过渡保留窄平滑区；家具高光另作块状处理。处理发生于3D材质逐灯light()，保留每盏灯的颜色和既有材质能量分配。多灯相加后仍可能得到更多明度，不能把这描述为最终画面仅有三种颜色。零直接光响应仍为零。

没有限定RGB调色板，也没有全屏换色。原2×2像素抖动仍在原ATTENUATION梯度限定的光照／阴影交界处理，新卡通层没有增加一张覆盖画面的网点层。角色精灵、人物描边、血液、玻璃和UI专用材质不进入本次架构／家具着色替换。

样板复用已认可的材质场景，通过继承创建独立入口，在原生生产美术GameTestLab房间运行。2049个活材质参与，其中架构类1964个、已认可家具85个。活材质对象保持不变，只切换各自Shader；切换时重新读取实际参数值，以保留原墙体剖切、反射捕获和其他所有者的参数更新。没有更改模型、UV、碰撞、灯光设置或战斗数值。

候选位于 `.runtime/toon_response_20261108/candidate/`。新Shader为本地编写的逐灯响应重映射。其输入仍由已认可材质的法线、粗糙度／反射响应和木纹遮蔽生成，未重新调整这些材质参数。19份已认可材质与正式来源文件的SHA256制作前后保持一致，见 `source_manifest.json`、`protected_source_check.json`。

## 实景与操作验证

最终 `camera02/`：原生Forward+/Vulkan、640×360世界画面、1280×720窗口、私有WASAPI静音，22项检查／0失败，进程退出码0并释放锁。

交付入口另经 `launch.ps1 -Diagnostic -EvidenceLabel entry01` 实际启动：PID61204，Forward+/Vulkan，输出 `TOON_SAMPLE_READY materials=2049`，退出码0并释放锁；日志无脚本或Shader错误。该检查使用试玩入口的同一场景与启动流程。

检查包括：实际GPU三段受光平台和零响应控制、房间架构与家具覆盖、材质参数保留、关闭着色后Camera逐像素恢复、原角色载体及描边不变、独立UI不受影响、真实T键双向切换、正常移动和镜头跟随、恢复后重新创建着色组件所得画面一致。关闭直接光后，着色开／关两幅画面完全一致，未增加自发光。

首轮 `camera01/` 的UI检查失败，原因为检查区域使用逻辑坐标，忽略根窗口2倍缩放，读取到了部分游戏画面。改为用实际stretch transform定位UI区域，确认1280×720输出中(56,52)、360×36区域逐像素一致。该修正只涉及验收脚本定位；没有通过修改UI渲染来回避失败。参考：[Viewport.get_stretch_transform](https://docs.godotengine.org/en/stable/classes/class_viewport.html#class-viewport-method-get-stretch-transform)。

实际房间固定画面中，着色开／关超过12/255的RGB最大通道变化为8095个像素，超过2/255为98479个；这是指定画面差异，不能代替用户对风格的视觉判断。截图和正常走动帧保留于 `camera02/`。

交付：`delivery/toon_comparison.gif` 为“已认可材质”与“材质＋三段卡通着色”的同机位／同灯光切换。上方是实际整间房Camera，下方是各自同机位的家具局部。仅标注、裁切及Nearest整数倍放大；两帧共用色表且关闭误差扩散，避免没有改变的像素出现压缩伪闪烁。无压缩PNG为 `accepted_material_window.png`、`toon_style_window.png`，并有 `toon_room_comparison.png`。
