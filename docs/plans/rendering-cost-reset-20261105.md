## 已核实的一手技术依据

1. [Godot4.7渲染架构](https://docs.godotengine.org/en/4.7/engine_details/architecture/internal_rendering_architecture.html)：Compatibility对带阴影的光采用额外绘制pass；Forward+用分簇光照筛选每像素相关灯。它有不同基础成本、颜色处理和特性，不能保证本项目更快。阴影图本身也不会因分簇光照自动免费。
2. [Godot4.7首用卡顿说明](https://docs.godotengine.org/en/4.7/tutorials/rendering/jitter_stutter.html)：Forward+/Mobile有ubershader预编译策略；Compatibility需要实际绘制首用材质／效果，可在实心全屏UI后准备。只load资源或隐藏物体并不能代替真实首画。电梯首次draw慢尚不等于已证实全部是编译。
3. [V Rising / Unity与Stunlock](https://unity.com/resources/stunlock-studios-v-rising)：按可见内容流送子场景及资产、优化批处理和运行数据；没有公开可直接复制的逐灯阴影缓存算法。文中entity baking不是光照烘焙。
4. [Project Zomboid 42 Techdoid](https://projectzomboid.com/blog/news/2022/02/42-techdoid/) 与[区块深度缓存说明](https://projectzomboid.com/blog/news/2023/02/play-your-cardz-right/)：缓存已绘制区块及深度，光照、门、切墙和内容变化时局部重画。其主体是固定视角2D瓦片，我们只借鉴变化才更新的原则，不能把本项目透视3D场景截成静图照搬。
5. [Godot LightmapGI](https://docs.godotengine.org/en/4.7/tutorials/3d/global_illumination/using_lightmap_gi.html)：静态直接／间接光可预计算，运行廉价但不能动态修改，也不提供准确动态反射。官方内置烘焙仅编辑器可用，导出游戏里随机生成新楼层不能简单调用它现场烘焙。

## 阶段二候选：固定环境光缓存＋动态受光，尚未授权全图实施

仅当阶段一证明收益空间，先设计同一样板里一段走廊和相邻房间的切换候选。房间／建筑稳定时保存墙、地面等受光贡献，材质着色器读取；室外光、人工照明分开，断电立即归零人工光；门、破墙、移动遮挡更新影响区，保留动态角色、家具、手电与枪口光的正确受光和遮挡。提前准备资源、缓存按变更失效，不每帧全图重算。

这是一套自定义缓存／混合照明设计，不是勾选LightmapGI。随机布局、墙体破坏、门口跨区、多个灯组组合、高度／法线、角色受光和反射遮挡都必须列出准确处理方式；全局断电或连续破坏不能集中重建造成新长帧。透视相机移动时不能直接冻结屏幕反射图，准确动态反射仍有独立成本。优先检查引擎已有缓存，避免重复实现无收益的缓存层。预算包含内存、初次构建、局部更新与运行帧，不用缓存名称代替测量。
